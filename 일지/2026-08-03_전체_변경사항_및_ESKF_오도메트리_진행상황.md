## 3. 현재 데이터 흐름

### 3.1 위치 추정

```text
/imu/data ───────────────────────────────┐
/gps ────────────────────────────────────┤
/lio_sam/mapping/odometry ───────────────┤
                                         ├─> src/eskf/scripts/eskf_node.py
/Ego_topic의 velocity.x, wheel_angle ─┐  │       ├─> /eskf/odom
/imu/data ─────────────────────────────┴─> /odometry/pure
                                             └─> /pure_odometry/diagnostics
```

- 순수 오도메트리는 `/Ego_topic`에서 `velocity.x`와 `wheel_angle`만 사용함.
- 순수 오도메트리는 Ego의 위치, heading, GPS 또는 LiDAR를 사용하지 않음.
- ESKF는 순수 오도메트리 속도를 계속 보조 측정으로 사용함.
- GPS가 정상일 때는 GPS가 절대 위치를 담당함.
- GPS 음영 때만 순수 오도메트리의 GPS 기준 상대 이동량을 위치 보조로 사용함.
- LIO-SAM은 연속성·정렬·퇴화 상태를 검사한 뒤 조건부 보조로 사용함.
- 최종 위치는 `/eskf/odom`, 기존 노드 호환 출력은
  `/localization/ego_status`로 발행함.

### 3.2 ESKF와 순수 오도메트리의 상태 차이

| 모듈 | 내부 상태 | 역할 |
|---|---|---|
| 순수 오도메트리 | `x`, `y`, `yaw`와 속도·조향·IMU 기반 누적 상태 | GPS 없이 짧은 구간의 차량 상대 이동을 안정적으로 추적함 |
| ESKF | `px`, `py`, `vx`, `vy`, `yaw`, `accel_bias_x`, `accel_bias_y`, `gyro_bias`의 8-state | GPS·IMU·LIO·순수 오도메트리를 불확실도와 NIS gate로 융합함 |

순수 오도메트리를 ESKF로 가져온 이유는 GPS 음영에서 IMU만 적분할 때 발생하는
속도·위치 드리프트를 차량 속도와 조향 정보로 제한하기 위해서임. 반대로 순수
오도메트리만 사용하면 장시간 누적 오차를 절대 위치로 되돌릴 방법이 부족하므로
GPS와 ESKF가 함께 필요함.

### 3.3 차량+사람 인식

```text
/velodyne_points
  ├─> 차량 PointPillars epoch 39 ──> 차량 검출 JSON
  └─> 보행자 far-v2 epoch 27 ─────> 보행자 검출 JSON
                                      │
                 동일 LiDAR timestamp로 결합
                                      │
                 차량 3D 박스 내부 사람 후보 억제
                                      │
        /lidar_detection/combined_detections
        /lidar_detection/combined_markers
```

차량과 사람 모델이 서로 독립된 단일 클래스 모델이어서 차량을 사람으로도 잡는
경우가 있었음. 통합 노드는 동일 LiDAR 프레임끼리 결합하고, 회전된 차량 3D
박스 내부의 사람 중심점을 중복 오검출로 제거함.

### 4.3 ESKF에 이식한 핵심 기능

- `/odometry/pure`의 signed speed를 연속적인 wheel-speed 측정으로 사용함.
- GPS 음영에서만 상대 오도메트리 위치 보정을 활성화함.
- GPS가 마지막으로 정상인 한 점을 상대 오도메트리 anchor로 사용함.
- 지연 GPS를 과거 시각에 반영할 때 IMU뿐 아니라 속도 이벤트도 다시 재생함.
- 순수 오도메트리가 이동 중이라고 판단하면 잘못된 ZUPT가 걸리지 않도록 막음.
- 순수 오도메트리 local jump를 탐지하고 진단 카운터로 노출함.
- GPS 음영 이동 거리에 비례해 오도메트리 위치 공분산을 증가시킴.
- 누적 pose covariance끼리 잘못 빼지 않도록 수정했음.
- ESKF 상태를 변경하는 ROS callback을 `threading.RLock`으로 직렬화했음.
- `/pure_odometry/diagnostics`의 `motion_rate_scale`을 ESKF가 읽도록 연결했음.
- MORAI 소스 timestamp와 실제 차량 물리 진행 속도가 다를 때 다음 계산에
  물리시간 비율을 적용함.
  - IMU propagation `dt`
  - GPS 유한차분 속도와 공분산
  - GPS 재획득 projection
  - 지연 GPS 분산
  - 오도메트리·SLAM lag 동기화
- 진단에 `odometry_time_scale`, `odometry_time_scale_updates`,
  `odometry_local_jumps`, ZUPT 차단 횟수 등을 추가했음.

## 8. 실행 중 발생한 이슈와 처리

1. 최신 분리 노드를 확인하려고 `sensor_fusion.launch`를 메인 launch와 중복
   실행했을 때 같은 이름의 `required` 순수 오도메트리 노드가 교체되면서 기존
   메인 `morai.launch`가 종료됐음.
2. 중복 launch를 즉시 종료하고 기존 실행 명령 `/home/bisa/.local/bin/2`를 같은
   인자로 다시 실행해 메인 launch를 복구했음.
3. 재실행 과정에서 기존 `run_morai.sh`의 WebSocket 자동 재연결 동작이 수행됐지만
   연결에는 실패했음. 포트·센서 수치·Time Manager 값을 새 값으로 편집하지는
   않았음.
4. 이후에는 사용자 요청에 따라 MORAI UI, Network 설정, 센서 설정 및 ESKF YAML
   수치를 건드리지 않고 읽기 전용 상태 확인만 수행했음.

- 이동 중 `/odometry/pure` 연속 발행
- `odometry_speed_accepted` 증가
- 실제 무작위 GPS 차단·재획득 구간의 위치 오차
- 장시간 `invalid_measurements`, local jump, filter divergence 여부
